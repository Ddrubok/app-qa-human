# 공급된 QA 기록 A–F 판정

작성일: 2026-11-10. 실제 실행일은 제공되지 않았다.

이번 작업은 서로 다른 제품·세션의 공급 기록을 정리한 문서 검토다. 제품을 새로 실행하거나 스크린샷을 촬영하지 않았으며, 원본 체크리스트·외부 시스템도 변경하지 않았다. 아래의 성공·실패는 원 실행자의 공급 기록에 귀속된다. 작성자가 재현한 결과가 아니다. 제품명, 빌드, 실행 환경, 계정 역할, 실행 시각, 상세 증거가 없는 항목은 미상으로 남겼다.

실행 지침의 `SKILL.md` 및 일반 참조 문서만 사용했다. 저장소의 evals 내용이나 평가 정답은 읽지 않았다. 이 파일만 요청한 출력 경로에 새로 작성했다.

## 근거와 판정 원칙

| 근거 ID | 공급된 사실 | 원 실행자 |
|---|---|---|
| S-A | PRD와 `설정 > 알림 > 시간` 경로를 이미 읽은 에이전트가 새 브라우저 창에서 해당 설정 변경에 성공했다. 요청의 관심사는 처음 쓰는 사람의 발견 가능성이다. | 에이전트 |
| S-B | 첫 시도에서 메뉴를 찾지 못하고 종료했다. 개발자가 `우측 상단 점 세 개`라고 알려준 뒤 설정 저장·재열기에 성공했다. | 미상; 외부 힌트 제공자는 개발자 |
| S-C | 이전 실행 기록 없이 숙련자 관점 검사를 요청했다. 자료는 제품 URL뿐이고 현재 브라우저 도구가 없다. | 실행 기록 없음 |
| S-D | supplied RUN-1에서 Help를 열어 저장 방법을 읽었으나 저장은 실패했다. RUN-2는 그 화면 학습 기록을 넘겨받아 같은 계정에서 저장을 시도했다. 결과 기록은 없다. | 미상 |
| S-E | 게임에 이동·공격 동시 입력이 필요하지만 도구는 키 하나씩만 보낼 수 있다. 플레이어가 패배한 뒤 재시작 버튼으로 다음 판에 진입했다. | 플레이어; 사람/AI 여부 미상 |
| S-F | `screenshots=off`, DOM 조작 가능, 이미지 없는 환경이다. 기존 체크리스트가 클릭 순서를 지정하고 JSON 소비자는 schema 2.0의 기존 필드만 허용한다. | 실행 결과 없음 |

기능 결과, 지식 경계, 경험 근거, 화면 관찰 범위를 각각 판단한다. 공급된 실행도 유효한 증거가 될 수 있으나, 현재 빌드에 대한 검증으로 옮기려면 기대 결과·빌드·환경·증거의 일치가 필요하다. 이번 입력만으로 그 일치를 확인할 수 없다. 실패나 혼란을 지우지 않되, 원인·요구사항 위반·재현성까지 만들어 내지 않는다.

schema 2.0의 실행 상태는 `not-run | passed | failed | blocked | not-applicable`를 유지한다. `informed`, `unverified`, `retest` 등을 실행 상태로 추가하지 않는다. 결과가 없는 과거 시도에는 임의의 pass/fail을 부여하지 않는다. 새로 제안하는 검증은 아직 실행하지 않았으므로 `not-run`이다.

## 현재 결과와 비교 가능 범위

| 사례 | 현재 단정 가능한 결과 | 경험 레벨 비교에 사용할 수 있는 범위 |
|---|---|---|
| A | 공급 기록상 설정 변경 성공. 실행 전 PRD·정답 경로 노출로 지식 경계는 `informed`, 수행 방식은 guided다. 재열기 후 값 유지 여부는 미제공이다. | 기능 수행의 참고 결과로 사용 가능. 무도움 cold L0 발견 성공으로 집계할 수 없다. 새 창은 모델의 지식을 지우지 않으며 신규 서버 계정도 입증하지 않는다. |
| B | 무도움 첫 시도는 메뉴를 찾지 못해 미완료. 외부 힌트 후 별도 시도에서 저장·재열기 성공이 보고되었다. 첫 결과와 도움 후 결과를 모두 보존한다. | 동일 흐름의 도움 전·후 관찰로 사용 가능. 힌트 후 성공은 unassisted L0 성공이 아니며, 자연 습득한 L2 숙련의 증거도 아니다. 최초 시도의 cold 경계 검증 자료는 없다. |
| C | 제품 실행 없음. 관찰 기반 숙련 근거도 없다. 요청된 L2 검사는 `not-run`이며, 브라우저 도구 부재는 실행을 준비할 때의 제약이다. | 현재 레벨 비교 결과로 사용할 수 없다. URL과 ‘숙련자’라는 역할명만으로 L2 경험을 만들 수 없다. |
| D | RUN-1의 Help 열람과 저장 실패를 보존한다. RUN-2는 동일 계정에서 저장을 시도했지만 결과 미제공으로 판정 보류다. | 실패한 이전 사용도 L1의 선행 경험이 될 수 있다. RUN-1의 관찰 학습을 사용한 RUN-2는 L1 학습 연쇄로 분류할 근거가 있다. 결과 비교는 아직 불가능하며 독립 사용자 비교도 아니다. L2 근거는 없다. |
| E | 패배 결과 및 재시작 후 다음 판 진입이 보고되었다. 재시작·재진입이라는 좁은 기능은 성공했다. 동시 입력 기능의 검증은 도구 제약으로 막혀 있다. | 손실·재시도 흐름의 근거로 사용 가능. 핵심 입력 제약이 있는 패배로 숙련도 효과, 게임 밸런스, 사람의 난이도 적합성을 비교할 수 없다. |
| F | 실행 결과가 아닌 실행 조건이다. 캡처는 금지되어 있고 시각 관찰이 없다. 지정된 클릭 순서는 guided 체크다. 기능 결과는 아직 없다. | 향후 허용된 DOM 기반 기능 검사는 가능하지만 시각적 cold L0 발견 가능성의 근거로 사용할 수 없다. 일반 DOM 조작을 실제 보조공학 검사로 바꿔 부르지도 않는다. |

A–F는 서로 다른 제품·세션이다. 이 표는 판정 방식의 비교이며, 경험 레벨별 성공률·우열을 계산하는 비교 실험이 아니다. 조건이 다른 기록을 모아 ‘초보자 대비 숙련자가 더 성공한다’고 결론 내릴 수 없다.

## A — 경로를 이미 안 상태의 성공

**보고서 표현:** “공급 기록 S-A에서 에이전트는 PRD와 설정 경로를 사전에 알고 설정 변경에 성공했다. 이는 경로를 안내받은 기능 수행 결과이며, 처음 접하는 사용자의 독립적 발견 가능성은 검증하지 못했다. 새 브라우저 창에서도 사전 지식은 유지된다.”

**남은 검증과 다음 행동:** 기존 기록을 `informed`로 유지한다. 설정 변경 성공이라는 공급 주장을 보존하되, 저장 과업 전체를 passed로 판단하려면 재열기·재로드 후 목표 값이 유지되는 관찰이 필요하다. 현재 그 단계는 확인되지 않았다. 최초 발견 가능성은 향후 별도 실행에서 중립적인 목표만 제공하고, PRD·정답 경로·기존 보고서가 전달되지 않았는지 확인해야 한다. 초기 온보딩·계정·저장 상태도 기록해야 한다. 독립 지식 경계를 확보할 수 없다면 유용한 guided 검사를 계속하되 cold 결과라고 주장하지 않는다. 이번에는 새 실행을 하지 않았다.

시작 전부터 경로를 알고 있었으므로 이를 우선 `informed`로 기록한다. 실행 중 금지 정보가 새로 유입되었다는 증거 없이 `contaminated`라는 사건을 추가하지 않는다.

## B — 실패한 첫 시도와 힌트 후 성공

**보고서 표현:** “공급 기록 S-B의 첫 무도움 시도는 메뉴를 찾지 못한 채 종료되었다. 개발자의 ‘우측 상단 점 세 개’ 힌트 후 이어진 별도 도움 시도에서는 설정 저장·재열기에 성공했다. 도움 후 성공은 첫 시도의 미완료를 대체하지 않으며, 무도움 발견 성공으로 집계하지 않는다.”

**남은 검증과 다음 행동:** 두 시도를 별도 run으로 보존하고 연결한다. 기존 run ID가 있으면 재사용하며, 없으면 가져오기용 안정적 ID를 한 번 부여하되 원 실행 ID와 혼동하지 않도록 한다. 첫 시도의 마지막 행동·종료 이유·상태와 힌트 내용·제공 시점·제공자를 기록한다. 외부 힌트는 무도움 시도를 종료시키며, 도움 시도의 지식 경계는 `informed`다. 최초 지식 경계를 확인할 자료가 없으므로 첫 시도를 ‘검증된 cold L0’라고 단정하지 않는다.

공급된 저장·재열기 성공은 해당 범위의 기능 성공으로 보존한다. 재열기 후 값 일치를 포함한 원 관찰, 빌드·역할·초기 상태를 확보하면 기대 결과와 더 정확히 대조할 수 있다. 메뉴를 못 찾은 사실은 사용성 마찰의 세션 증거다. 기대 동작과 실제 화면 조건이 없는 상태에서 메뉴 결함이나 모든 초보자의 실패로 확대하지 않는다. 이후 같은 사람이 반복한다면 과거 학습과 외부 힌트를 모두 표시해야 하며, 이를 순수한 관찰 학습이나 검증된 L2 숙련으로 세탁하지 않는다.

## C — 숙련 근거와 실행 도구가 모두 없음

**보고서 표현:** “L2 관점의 검사는 계획 상태다. 이전 제품 사용·관련 과업 숙련의 증거가 없고 브라우저 실행 도구도 없어 제품을 실행하지 않았다. L2 결과는 not-run이며, 성공·실패·숙련자 효율에 관한 결론은 없다.”

**남은 검증과 다음 행동:** 목표 과업·완료 기준·빌드·허용 환경을 정리하고, 기존 사용 기록이나 앞으로 실제로 관찰한 관련 핵심 과업·복수 동작의 숙련 근거를 확보해야 한다. 세션 수나 승리 횟수만으로 L2를 정하지 않는다. 사용 가능한 실행 도구가 마련되면 해당 범위를 검사한다. 허용된 별도 목적에 따라 지식을 주입한 검사도 가능하지만 `seeded` 또는 `mixed`로 밝혀야 하며 습득된 숙련으로 표기하지 않는다. 현재는 주입할 제품 지식도 제공되지 않았다.

브라우저 도구가 없다고 제품 자체를 실패 처리하지 않는다. 실제 시도 중 차단된 기록도 없으므로 가상의 blocked 런을 만들지 않는다. URL을 가졌다는 사실만으로 화면·동작·소스 검토가 끝났다고 쓰지 않는다. 이번 작업에서는 도구를 설치하거나 새 제품 실행을 시도하지 않았다.

## D — 실패한 사용 경험도 L1로 이어질 수 있음

**보고서 표현:** “공급된 RUN-1은 제품 안의 Help에서 저장 방법을 읽은 뒤 저장에 실패했다. RUN-2는 RUN-1의 화면 학습을 넘겨받아 같은 계정에서 저장을 시도한 L1 학습 연쇄다. RUN-2 결과는 아직 제공되지 않아 성공, 실패, 회복 여부를 판정할 수 없다.”

**남은 검증과 다음 행동:** RUN-1·RUN-2의 기존 ID와 실패 이력을 그대로 유지한다. Help는 제품 내부에서 발견한 도움으로, 개발자의 외부 힌트와 구분한다. RUN-1에서 허용된 표면으로 Help를 발견했다면 Help 열람 자체는 무도움 시도를 외부 도움 시도로 바꾸지 않는다. 다만 전체 최초 지식 경계의 검증 여부는 제공 자료만으로 알 수 없다.

지식 기록에는 ‘Help에서 읽은 저장 안내’의 출처를 S-D/RUN-1에 연결하고, `origin=observed`, `learned_in_run=RUN-1`, 미상의 빌드는 null로 남긴다. 정확한 안내 내용은 미제공이므로 만들어 넣지 않는다. ‘안내를 읽었다’는 학습과 ‘그 방법으로 저장이 성공한다’는 기능 사실을 구분한다. RUN-2의 이전 실행 참조는 RUN-1을 가리킨다. 진단·소스·내부 원인은 사용자 학습에 섞지 않는다. 전달된 내용과 도구 경계를 실제로 확인하지 못했으므로 전체 경계를 임의로 `verified`라 하지 않는다.

같은 계정의 재사용은 명시하지만 저장 실패 후 남은 값, 온보딩, 미저장 입력, 서버 상태는 미상이다. 동일 계정이 저장 지속성을 입증하지 않는다. RUN-2의 마지막 행동, 저장 응답, 재열기 후 값, 초기 상태, 빌드·환경 기록을 받아야 결과를 판단할 수 있다. 실행을 시도했다는 사실이 있으므로 이 과거 기록을 ‘실행하지 않았다’로 바꾸지 않으며, 원인 미상의 결과 누락을 `failed`나 `blocked`로 추정하지 않는다. 엄격한 schema가 미확정 과거 시도를 표현하지 못하면 공급 기록을 동반 문서에 보존하고 결과 확보 후 실행 상태를 확정한다. 별도로 제안하는 재열기 검증만 `not-run`으로 둔다.

이 연쇄는 RUN-1의 성공을 전제로 하지 않는다. RUN-2 결과가 나와도 같은 계정과 학습이 이어진 의존적 연쇄로 보고하며, 독립 L0/L1 사용자 비교나 L2 숙련 검증으로 확대하지 않는다.

## E — 동시 입력 제약과 패배·재시도 흐름

**보고서 표현:** “공급 기록 S-E에서 플레이어는 패배 후 재시작 버튼으로 다음 판에 진입했다. 패배·재시도 흐름은 관찰되었으나, 도구가 이동·공격 동시 입력을 지원하지 않아 핵심 조작의 정상 수행은 검증하지 못했다. 패배만으로 게임 결함이나 난이도 문제를 판단하지 않는다.”

**남은 검증과 다음 행동:** 기능을 나누어 기록한다. ‘재시작 후 다음 판 진입’은 공급 기록 범위의 passed로 보존할 수 있다. ‘이동과 공격 동시 수행’은 구체적인 도구 제약 때문에 blocked이며, 제품이 동시 입력을 거부했다는 증거는 없다. 승리·보상 정산·진행 저장·복귀 등 공급되지 않은 단계는 아직 not-run이다. 패배 흐름을 검사하기 위해 반드시 승리할 필요는 없다.

향후 동시/누름 유지 입력을 지원하는 기존 도구나 실제 조작 환경에서 핵심 동작을 검사하고 정상 입력의 결과를 확인해야 한다. 이를 현재 환경에서 키를 번갈아 보낸 결과로 대체하지 않는다. 입력 제약이 패배의 원인일 가능성은 있으나, 패배 원인이라고 확정할 자료도 없다. 레벨을 비교하려면 같은 빌드·목표·역할·입력 조건과 각 레벨의 지식 근거를 맞춰야 한다. 이 기록만으로 재미, 숙련자 전략, 사람의 반응 속도 또는 장기 유지율을 판단하지 않는다.

## F — 스크린샷 OFF, 지정 경로, 엄격한 JSON 계약

**보고서 표현:** “screenshots=off를 유지하며 새 이미지 캡처는 수행하지 않는다. DOM으로 가능한 기능 검사는 지정된 클릭 순서의 guided 검사로 계획한다. 이미지가 없어 시각적 발견 가능성·가독성·겹침·대비는 검증하지 못한다. 현재 제공된 실행 결과가 없으므로 기능 검증도 아직 not-run이다.”

**남은 검증과 다음 행동:**

1. **관찰 범위:** 새 스크린샷 호출, 자동 이미지 반환, 간접 캡처 우회 모두 하지 않는다. 향후 허용된 DOM/텍스트/파일 증거로 동작과 결과를 검증할 수 있다. 이미지가 없다는 이유만으로 기능 실패를 선언하지 않는다. 반대로 DOM에 요소가 있다는 사실만으로 화면상 가시성, 포인터 도달 가능성, hover, 대비를 통과시키지 않는다. 핸들러 직접 호출이나 상태 주입은 사용자가 그 동작을 수행할 수 있다는 증거가 아니다. 실제 보조공학 표면을 사용한 경우에만 assistive 관찰로 명시한다.
2. **체크리스트 보존:** 원 ID, 원문·사람 메모, 클릭 순서, 기대 결과와 출처/개정, 구현 상태, 과거 실행을 보존한다. 이 요청은 보고서 정리이므로 원본을 변경하지 않는다. 경로를 지정한 체크를 독립적 발견 테스트로 바꾸지 않는다. 체크 표시나 구현 완료만으로 passed를 만들지 않으며, 기대 기준이 불명확하면 해당 판정을 보류한다. 현재 적용 여부가 미상이면 과거 성공을 현재 통과로 승격하지 않는다.
3. **기능 완료:** 실제 허용된 실행이 이루어진 뒤 저장·재열기 등 관찰 가능한 완료 조건으로 판정한다. 버튼 클릭이나 성공 토스트만으로 과업 완료를 선언하지 않는다. 도구 제약은 의존하는 속성에만 적용하고 독립적으로 가능한 기능 검사를 전부 막지 않는다.
4. **schema 2.0 호환:** `schema_version: "2.0"`, 기존 필드 이름, 기존 실행 상태 enum을 유지한다. 소비자가 허용하지 않는 `experience`, `handoff_contract`, `checklist_verification`, `applicability`, `run_history` 등의 새 키를 JSON에 추가하지 않는다. 소비자가 이미 허용한 `sources`, `limitations`, `actual_result` 같은 필드 안에서 필요한 한계를 표현하되 계약의 타입도 유지한다. 추가 경험·학습·도움·적용성·이력 정보는 기존 case ID와 run 참조에 연결한 별도 동반 기록으로 보존한다. 소비자가 run ID 필드를 허용하지 않으면 외부 매핑에 기록하며 새 키를 강제로 넣지 않는다.
5. **내보내기 검증:** 실제 JSON 산출 요청이 생기면 기존 허용 필드 목록과 타입, 파싱, 상태 enum, ID 연결, 원문·이력 보존을 검증한다. 현재는 소비자의 상세 스키마나 원본 JSON이 제공되지 않아 실제 계약 검증을 수행했다고 주장할 수 없다. 새로 계획하는 케이스는 `status=not-run`, `actual_result=null`, `evidence_refs=[]`로 두고 요구사항 출처를 실행 증거로 넣지 않는다.

이번 작업 전체는 문서 검토이므로 런타임 스크린샷 커버리지는 not-applicable이다. F의 향후 실행 옵션은 별도로 `off`/`disabled`를 유지한다. 어느 경우도 이미지 검토 완료로 표기하지 않는다.

## 남은 검증의 우선순위

현재 가장 직접적으로 부족한 것은 A의 독립 발견 증거, C의 숙련·실행 근거, D의 RUN-2 결과, E의 정상 동시 입력, F의 실제 실행 결과다. B의 첫 미완료와 도움 후 성공은 둘 다 보존한다. 모든 사례에서 현재 제품으로의 적용을 주장하려면 빌드·환경·기대 결과·출처를 추가로 맞춰야 한다.

기능 성공이 cold 발견 가능성을 증명하지 않으며, 경험 경계의 한계가 이미 보고된 기능 성공을 자동으로 무효화하지도 않는다. 공급 기록의 실패·도움·도구 제약·결과 미상을 각기 남겨야 다음 검증을 정확하게 선택할 수 있다.
